# P40-16S｜跨區合併請款、8 月／10 月多發票、逐原單折讓與部分收款 — 隔離驗收

> **完全隔離、禁止正式入帳或合併。** 此候選分支只新增測試與設計報告，沒有修改正式 `main`、`beta`、Supabase 或任何正式請款、發票、薪資、銀行及對外 PDF。所有識別以 `SYNTH-` 開頭，金額不代表真實建商核定。

## 實際正式 ERP 規則（2026-11-17 唯讀檢查 GitHub main 原始碼）

- `assets/js/billing-groups.js` 的 `openEditor()` 對外明細使用 `targetBillingId` 選定單一目標案場，統一編排 A＋B 施工明細，**原請款、發票及應收各自保留，合併文件不另計一筆應收**；已開發票仍附在各自原單。
- `assets/js/invoices.js` 的 `openOriginalBillingInvoice()` 明確只編輯 `sourceType='billing'`、`sourceId=原請款單 id` 的原單發票，不在合併群組 id 新增或分攤發票。
- `assets/js/external-billing-print.js` 的 `originalTemplateView()` 對外 `mergedBillingProjects` 只有 `displayProjectName` 一個案場；保留施工明細，並用印表專用發票狀態而**不將各張原發票號、日期、原單對應金額**投影到對客 PDF。
- `assets/js/erp-store.js` 的 `invoiceRows()`、`saveInvoice()` 保持 billing 來源；`commissionReleasePool()` 與 `commissionAllocationReleaseState()` 以原始員工抽成分配、收款解鎖與已結算鍵限制支付。這些均只是唯讀核對正式程式，不代表新折讓功能已接進正式 Store。

## SQL 行為與需要阻擋的錯誤

1. `.p40-16s-tests/synthetic_group_invoice_ledger.sql`：只在 GitHub CI 一次性 PostgreSQL 16 `p40_16s_ci` 中建立 `p40s_lab` 私有 schema；兩張虛構 source，兩張分別對應 8 月/10 月的原單發票、兩筆本身的收款/保留款餘額、一個合併文件顯示目標。
2. 受限的 `p40s_clerk` 只能呼叫假交易 RPC，`p40s_public` 只能讀取清洗過的 customer projection。沒有帳務表的直接 UPDATE/INSERT/DELETE 權限。**這是 PostgreSQL 假帳號模型，不代表 Supabase shared `authenticated`、MFA/JWT/RLS/GRANT 已驗證；SQL 的 SECURITY DEFINER 禁止複製到正式站。**
3. 每筆 `CREDIT` 必須指定自己的原單發票、假建商核准與折讓憑證號、未稅/稅額拆分，且此原單還沒有收款/保留款與前次折讓。其他原單已收款不會讓這張原單被錯誤合併計算。
4. `RETENTION_SET` 按**各自折讓後原單**5%/10% 比例驗證；一般 `AR_RECEIPT` 不得超過各自 `有效金額-保留款`，保留款收回必須正常應收已收齊；**銀行流入是所有獲准收款交易之合計，合併文件不再新增銀行或第三筆應收**。
5. 兩種收款都必須引用相符的原單發票。L 區收款不能借用 M 區發票；把合併金額任意轉到單區、重複收款、超收保留款都要拒絕。
6. 抽成來源與已核准的未稅基數、比例、員工 ID 對應；原型僅在**該張原單正常應收收齊**時允許抽成核計。示例未稅 14,000 × 50% = 7,000；兩員工各 25% = 3,500。**原型不會重新分配已付款薪資，也不會直接付款員工。** 真實按戶別、部分收款解鎖、不同施工日的分配規則仍需完整獨立驗證。
7. 所有假交易同一 PostgreSQL row lock 中同時檢查 `sync_version` + `ledger_version`、引用憑證，追加不可修改的事件及更新原單與銀行投影；重送同鍵同內容為 DUPLICATE，換原單／發票／金額沿用同鍵必須拒絕。舊版本搶寫只有一筆能成功。
8. `p40s_lab.public_document()` 對外只回傳選定 M（或改選 L）案場名稱、**一份合併施工明細**與合計，刻意沒有原請款 ID、發票號碼、月份、每區金額、折讓來源、銀行或員工資料。與正式 PDF 設計方向一致，但**不是原版 PDF 的真正渲染驗收**。

## 仍未解除的正式阻擋

- **法律與會計**：虛構折讓證明 `SYNTH-APPROVAL-*`、`SYNTH-CREDIT-*` 是一般測試字串，不是國稅局法定折讓單、建商有效核准或真實 8/10 月發票。多張發票的折讓年份、銷項營業稅核定、原單扣款、已收款退款、保留款重分配尚未由會計核定。
- **資料模型**：僅 L/M 兩張虛構原單、各一張假發票；不能概括多區、多發票拆票、多付款銀行/手續費、發票作廢補開、折讓沖回、跨月份營業稅與多案場真實資料同步。**本階段沒有修改/發明正式折讓 API**。
- **版本與舊客戶端**：正式 `erp_states.data jsonb` 仍有原本 REST/legacy 回寫；候選台帳只存在隔離 SQL，沒有真實 Supabase Auth/RLS 與全量版號護欄，也沒有實際手機 Chrome 或原版 IndexedDB/Emergency/雲端同步整合。
- **對外文件**：本測試的 public projection 不是正式 `external-billing-print.html`/PDF 實體列印，尚未驗證真實 A4 單頁、施工明細、跨區選區、內部發票資料不外露；正式外部 PDF 完全保持現狀。
- **薪資**：測試歷史已付薪資是不可變的假紀錄；真實員工抽成分配必須考慮薪資是否已付、業績按戶別、是否收清、未稅/含稅、不同員工與合法更正方式。不得自動更正真實員工已付薪資。

## CI 驗收/正式發佈規則

- 新增 44 項實際 PostgreSQL 交易測試、9 項對**正式原始碼的唯讀文字契約查核**，及 P40-16R/Q/O/A-D/I/K 已驗證的 169 項合成回歸。
- CI 使用 branch 的 main/beta SHA 閘門、只允許新增 P40-16S 測試檔，禁止任何正式 HTML/JS、Supabase schema/現有資料、對外 PDF 變更。
- **任何 CI PASS 僅限隔離模型。** 不得由此推論正式折讓可以入帳，也不得直接合併包含 P40-16A～R 的所有草稿。
- 未來正式上線必須從當時最新 main 最小候選開始，在取得最新 SYNCED、完整安全備份、真實兩裝置全流程、原單/發票/會計憑證、薪資抽成、銀行與對外 PDF 驗收後，再取得使用者**獨立明確正式發布與修改真實資料授權**。任何阻擋出現即停止。

**目前正式 ERP 繼續使用 P40-15C 唯讀議價折讓試算。**
