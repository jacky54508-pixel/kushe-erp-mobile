## 1. 實際正式主程式的規則與尚缺的核准

已核對 `assets/js/erp-store.js` 的 `externalBillingUnified()`、`saveExternalBillingDocument()`、`externalBillingDocumentIndex()`，以及 `assets/js/external-billing-print.js` 的 `validate()`：

- 每張正式對外合併文件具 `schema`、`id`、`revision`、`sourceIds`、`targetBillingId`、`sourceSnapshots`、`settlementSnapshots`、`totals`、`unified` 及 `history` 等欄位。
- 正式儲存會比對 `expectedSnapshot`，防止在原單、收款或文件變動後直接用舊畫面覆寫；正式儲存成功後 `revision` 增加 1，既有版本記入 `history`。最多 50 版，不能清除以前的核對紀錄來延長版次。
- 正式跨區核對會比較原單施工戶別／品項／單位／數量／單價，及統一明細和原始未稅或含稅總額；不同時要求填 `unified.reason`、勾選已核對。**現有的原因文字與勾選框並不等於可信、獨立的核准人簽章。**
- 正式 `printSaved()` 可以從已存的 `history` 選擇保存版本。**既有已確認且有重編理由的文件，目前仍可列印**；本階段不應直接新增會把大量正式文件全部擋住的門禁。

## 2. P40-16AX 的獨立核准模型（只有虛構資料）

`.p40-16ax-tests/mock_approval_gate.cjs` 建立純記憶體、**不是 ERP 模組**的測試契約：

| 核准要件 | 隔離模型的行為 |
|---|---|
| 文件來源 | 呼叫**正式 main 的原有 `validate()`** 核對原單金額、保留款、收款及統一施工明細，再將假文件複製到模型記憶體；不取得任何真實 ERP 快照 |
| 版次 | 新存版本只能在前版 `expectedRevision` 相符時 `revision+1`；舊版維持檢視記錄，不能沿用舊版核准 |
| 核准指紋 | 使用 SHA-256 綁定模擬公司、文件、原始來源快照、統一明細、含稅/未稅、核定總額、保留款、收款、指定區、備註與版次；欄位排序正規化後指紋一致 |
| 編輯與審查 | **暫定的測試規則**：假會計／管理者可以編輯；僅假 `owner/admin` 且**不是當次編輯者本人**可以獨立核准。這不是使用者正式確認的角色政策 |
| 對外查核 | 同一公司、已授權文件、有效假 MFA、**目前**保存版本、有效原單指紋及該版獨立核准均吻合才發出**核准狀態中繼資料**；**不輸出原始客戶、發票、銀行、薪資或 PDF 檔案** |
| 修改失效 | 新版本只要戶別、品名、單位、數量、單價、列次、備註、來源、稅金、收款、目標案場、客戶或版次改變，舊核准一律無法授權**新版本**。重新核准前不能在此**測試模型**領取新核准狀態 |
| 稽核 | 測試用追加式稽核事件依序記錄建立／核准／修訂／再核准，以及前筆雜湊，**只保存指紋及假身分 metadata**，不存來源發票／施工列原文 |

**明確的安全限制：** 這個 `MockTrustedApprovalGate` 只有假的 session handles、假的 MFA 欄位和記憶體事件。SHA-256 雜湊本身**不是數位簽章、持久證據、身分驗證、PDF 完整性保證或正式帳務核定**。只靠記憶體物件，還不能抵擋真實伺服器及儲存權限遭破壞、重啟、競爭與時鐘問題。正式環境還需要具持久性且經過授權的審查紀錄、真實 JWT/MFA、公司與文件 ACL，以及核准前和交付前的可信原單來源比對。

## 3. 要求的真實業務驗收，不可被模擬 CI 取代

此模型特別不與正式 `saveExternalBillingDocument` 串接，也不修改 `assets/js/billing-groups.js` 或 `assets/js/external-billing-print.js`。原因是如果直接把模擬核准門禁掛到正式版，在沒有真實審查後台時，**既有已保存且合法的跨區請款會被無法核准的規則全面攔截**。需要先決定哪些角色可以審查、是否需要雙人覆核、歷史文件如何補核以及核准是否只針對對外施工重編，不得擅自把「核對理由」強行改成已簽署核准。

正式尚未完成：單筆可信資料來源、持久且防竄改的核准簽章／審查人、真實 Supabase JWT/MFA/公司角色、正式歷史資料移轉、原始 PDF bytes 完整性、真實公司 LOGO／大小章、手機電腦核對、最新 SYNCED、完整可還原備份、全請款／應收／多月發票／折讓／稅額／保留款／薪資抽成／銀行回歸，以及負責人**另外明確同意發布**。

## 4. 結論與下一個具體技術阻擋點

這個隔離試驗要證明：**施工重編核准不應只是一段說明，而應綁定當前版本的原單來源及每筆施工內容；保存新版本後必須重新核准。**

但 **P40-16AX 的正式發布狀態仍是 BLOCKED**。要繼續正式整合，真正先要解決的是**可信核准來源與 ERP 已儲存版本之間的信任邊界**；不能靠使用者自行送的公司、角色、核准布林值或整份 ERP JSON 快照當授權。需要獨立安全設計和使用者另行確認，不能因 CI PASS 就直接把模型合併到正式站。

測試 `.p40-16ax-tests/test_revision_approval.cjs`；獨立 CI `.github/workflows/p40-16ax-revision-approval.yml`。所有資料皆 FAKE，不讀取任何使用者資料，CI 不連 Supabase。
