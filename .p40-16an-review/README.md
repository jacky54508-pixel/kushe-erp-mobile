## 測試範圍

測試程式 `.p40-16an-tests/compare_official_to_candidate.py` 對同一個完全虛構的跨區合併來源使用：

1. **正式版對照樣本**：從正式 `assets/js/external-billing-print.js` 唯讀擷取原始的 `validate()`、`originalTemplateView()`，配合原始 `assets/js/external-billing-invoice.js` 驗證來源；將其對外 View 直接交給**完全未改動**的 `billing-print.html?print=0`，使用 Chromium 真正輸出 PDF。
2. **新原型樣本**：同份虛構來源，透過 P40-16AM 獨立轉接器與瀏覽器 `pdf-lib` 真正輸出 PDF bytes；不是把畫面高度當作 PDF 頁數。
3. **獨立檢查**：PyMuPDF 重新解析兩份 PDF 的頁數、A4 尺寸、每個虛構戶別、指定的唯一區域、所有內部發票資料不得出現；取第一頁渲染 PNG 並產生**兩份圖像並排**，同時紀錄標題字級、公司 logo 佔位尺寸、印章顯示區、施工明細與底部分組彙總是否存在、整頁圖像差異程度。
4. **純虛構圖像**：測試攔截任何 `enterprise/index.html` 的來源及影像要求，只以記憶體中性 SVG 方框取代公司 logo／大小章；**不擷取、不提供任何公司原始章印、銀行／發票、真人資料或字型檔**。
5. 使用 8、18、30 筆虛構跨區明細，並分別在 1280px 桌面及 390px 手機**模擬瀏覽器**執行。後者不是實體手機驗收。

## 已由原始程式碼確定、需獨立視覺測量的差異

| 項目 | 正式 `billing-print.html` | P40-16AM 新原型 |
|---|---|---|
| 公司名稱標題 | CSS `21pt`、綠色、粗體及完整英文抬頭 | 簡化黑白測試抬頭約 `11.3pt` |
| 對外單據標題 | 獨立 `h2`，CSS `21.5pt` | 與測試頁抬頭合併顯示 |
| LOGO | 預留 `18×14mm` | 模擬方框 `18×14mm`；**非真實 LOGO** |
| 大小章 | 正式跨區列印 CSS `.invoice-group-document .seal-wrap` 高 `19mm`，正式印章影像高度上限 `18mm` | 模擬章方框 `54×24mm` |
| 施工明細及底部彙總 | 正式密集版由來源戶別／品項數啟動，採原表格樣式和金額欄位 | 新原型固定原施工表及雙欄底部彙總 |
| 備註及金額區 | 正式備註為全寬獨立區塊、金額摘要及章印依正式 CSS 流程排列 | 新原型備註／金額使用固定底部左右兩欄 |

這些差異都不應視為「已完成正式排版」；**即使 PDF 都是 A4 單頁、金額完整，仍然可能不符合原公司抬頭及大小章位置要求**。

## CI 及發布門檻

- CI 若全綠，只代表**兩份真正 PDF 生成與「找到差異」的測試成功**。本階段的 `production_visual_parity` 強制保持 `BLOCKED`，不能宣稱新原型已與正式版視覺等效。
- 如原版 PDF 在某個測試案例超頁、短合併未顯示個別原施工戶別，應留下實際測試證據，不得藉由靜默修改原正式 HTML 讓測試通過。
- 不納入正式 LOGO、真實公司大小章、實際客戶資料；正式章位及真實手機／電腦驗收需要另行明確授權。
- 未來若需更改正式 PDF，必須另從屆時最新 main 開**最小實際候選**，先最新 `SYNCED`、完整可還原備份、差異審核、所有業務／金額／發票隱私回歸與實體手機／電腦 PDF，最後由使用者**另行明確同意正式發布**；任一不符即停。

**結論：P40-16AN 是視覺差異報告，不是正式發布或新版型更換授權。**
