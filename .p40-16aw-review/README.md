## 1. 已修正的**獨立候選**：對外備註中的已知敏感來源

正式 `assets/js/external-billing-print.js` 原本 `originalTemplateView(payload,d)` 將 `d.note || template.publicNote` 原樣變成 `publicNote`。即使建商版的 `sourceSnapshots` 和原發票對照不外傳，**使用者仍可能在備註中手動輸入其他區域名或原發票號碼**。

本候選新增**唯一正式來源程式修改**：`assets/js/external-billing-print.js` 的一個小型 `assertCurrentCustomerNotePrivacy(payload,d,publicNote)` 函式及呼叫。它：

- **只作用於非歷史的跨區對外建商版 `originalTemplateView()`**；原本的 `validate()` 及原發票投影、財務合計、原始施工明細／戶別、備註內容、歷史列印和其他正式頁面**都不改**。
- 將備註與**已知存在於此份原單來源**的其他區域 `projectName`、`invoiceNo`／`invoiceId`／`invoiceDate`、`billingId`、`receivableId`、原單顯示編號及施工列中的原發票 ID 對照（僅於本次記憶體中比對）。
- 比對過程以 NFKC 正規化、忽略大小寫及部分空白分隔，降低只是改大小寫或加入空白造成的漏判；同時對極短 ID 設定最短長度，避免普通一兩個字母就誤擋整篇備註。
- **發現符合的來源資訊就整份拒絕對外列印**，不自動移除備註、不偷偷改字句、不回寫任何來源資料。錯誤訊息只說明必須人工確認，不回顯私人票號或來源名稱。
- 一般內容、現場修繕說明及不含來源識別的正常備註均保持**原樣**；不降低原請款數字或對外 PDF 字體。

**刻意保留的限制：** 這不是完整 DLP 資料防漏系統，只能擋住「已知原單識別」的內容。未存在於來源欄位的客戶私人電話、額外個資、手工寫的其他項目、私人收款說明、重新拼寫或其他模糊描述，**仍可能**無法辨識；正式對外備註依然需要人工逐份檢視並簽核。對外列印的 URL hash 仍為編碼不是加密，這個候選沒有變更既有 browser `window.print()` 或新增 PDF-first 網關。

## 2. 重編施工明細：現在不能只靠一段「核對理由」視為真正授權

經核對**正式** `validate()`：

```text
same := 所有原單稅別與統一明細稅別相同，
        且原始各戶別／項目／單位／數量／單價與統一明細相同
if !same and !unified.reason.trim(): STOP
```

原來的檢查只是「內容有不同就要求填寫理由」。只要資料合計相符且理由非空，**沒有**核對可信 reviewer 的身分、核定時間、公司、文件版本、原施工來源 fingerprint、核准後是否再被修改。

本次**不擅自封鎖合法的既有跨區重編文件**，因為正式端目前沒有可信伺服器審核來源，直接加這項限制可能讓已經大量使用的合法建商文件無法輸出。相對地，新增**完全獨立的虛構核准模型測試**：只有經假受信任審查者登錄的公司、目標原單、原施工＋統一明細 SHA-256、核定帳款及文件版本一致才允許重編；寫在 client `reason` 或自稱已核定的客戶端物件不能取代外部審核；一旦版次、戶別／項目／金額、來源公司或目標區被改，必須拒絕。這**只是一個測試契約**，沒有正式簽章、伺服器身分驗證或不可竄改的授權紀錄，**不代表正式 ERP 已具備正式核准機制**。
