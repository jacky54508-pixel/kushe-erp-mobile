## 已核對正式 main 的規則

- `assets/js/auth-gate.js`：前端角色 `owner`、`admin`、`accounting` 可檢視與編輯請款，`employee` 不可以。前端 MFA 公司成員資訊**不是**新 PDF／核准服務的可信伺服器端 JWT 或 RLS 驗證。
- `assets/js/erp-store.js`：`saveExternalBillingDocument(values)` 具有 `expectedSnapshot` 衝突檢查、原帳務金額查核、`revision+1`、`history` 與既有確認／草稿規則。**任何核准設計不能修改原帳務、保留款、發票、收款、銀行、薪資或抽成**。
- `assets/js/billing-groups.js`：`printSaved(id,revision,historyOnly)` 會判定現行與歷史列印路徑，遇原請款／收款異動會擋住現行列印，舊版仍可從版本紀錄開啟。**既有合法文件不能因新增新式核准流程而被全面鎖住**。
- `assets/js/external-billing-print.js`：正式 `validate(payload)` 核對原請款施工列、計價、稅額、保留款、應收與收款。虛構測試直接逐字擷取**正式**函式執行，沒有自行建立替代會計計算器。

## 隔離操作設計

新增 `.p40-16ba-tests/approval_flow.cjs`，僅針對 `FAKE-` 公司、角色、跨區合併文件建立**記憶體狀態機**：

| 操作入口 | 測試權限 | 流程規則 |
|---|---|---|
| **編輯新版本** | 會計／管理者／負責人 | 舊文件先保留，另存新 `revision`；原始施工及金額須通過正式驗證，來源 SHA-256 改變會使舊核准不適用。送審中的版本需先退回或撤回 |
| **送審** | 被授權的編輯角色 | 只能送目前編輯中的版本；需有重編施工明細及理由，綁定文件 ID、版本、來源摘要與送審者 |
| **核准** | 暫定負責人／管理者 | 不可與編輯者或送審者為同一人；須重新核對當前版本及摘要；核准只控制該份重編文件可否**進入下一道對外 PDF 安全驗證**，不代表帳務改價 |
| **退回修改** | 暫定負責人／管理者 | 必須附核對理由；退回後需編輯並保存新版本，才能再次送審；不刪原文件或原核准歷史 |
| **查看歷史** | 有此文件閱讀權限的會計／管理者／負責人 | 使用正式原有的歷史列印概念，歷史只讀且與當前版本核准分離，不會強制舊文件追溯補核 |

**注意：表中角色分工與「必須不同人核准」是隔離候選設計，並非公司正式已核准制度。** 真實權限、審查人資格、補登舊版流程需要負責人另行決策。

## 可以操作的虛構介面原型

`.p40-16ba-demo/index.html` 是單一 HTML 檔案，可在瀏覽器開啟。清楚標示「**虛構資料、不是真實核准**」，有分段進度、請款摘要、虛構角色切換、編輯／送審／核准／退回／查看歷史及操作紀錄，支援桌機和窄螢幕展示。

介面**沒有**連接 Supabase、正式 ERP、GitHub Pages、Cloudflare、登入、上傳、網路請求、localStorage、PDF 生成或任何真實資料。其 UI 操作為人機互動示意，**不等同** Node.js 安全狀態機、真實身份核准或財務流程。本階段的 CI 只驗證原始碼契約與部分靜態介面條件，並非真的手機/桌機使用者視覺驗收。

## 必須阻擋的錯誤

虛構測試檢查：跨公司、沒有文件 ACL、員工無請款權限、模擬 MFA 不符、假 JWT 或停用帳號、編輯者自己核准、未送審就核准、版次過舊、送審中被修改、缺少退回理由、退回後不修改就重送、重複核准、舊版核准套用新版、原帳務被任意改價、原發票資訊進入核准中繼資料、員工查看歷史等。

**正式限制仍未解除：**
1. 真實 Supabase 尚無已驗證的單筆請款可信來源與安全資料同步／核准寫入流程；不能將整份 ERP 快照交給新 PDF 服務。
2. 尚無獨立可信的真實 JWT 簽章、MFA AAL2、公司會員及逐文件 ACL、後端核准授權、永久防竄改記錄。此測試雖用 SHA-256 追蹤版本，但 SHA-256 本身不是數位簽章。
3. 對外備註的任意文字敏感資訊與既有 P40-16AW 草稿中的隱私阻擋仍待正式採用決策；不能宣稱已保證所有 PDF 不外洩。
4. 真正 PDF bytes 驗證及唯一同檔交付、A4 單頁、完整施工項目、原公司 LOGO／章印、手機／電腦實測尚待完成。
5. 最新 `SYNCED`、完整且可還原的安全備份、最新 GitHub main／CI、完整請款／保留款／議價折讓／多月發票／銀行／薪資抽成回歸，以及**負責人另外明確同意發布**仍是硬性門禁。

**結論：P40-16BA 只驗證「正式請款核准介面應如何分工、進出哪些狀態、如何不阻擋既有文件」，不進行正式 ERP 修改或部署。** 已儲存的真實單據及員工薪資資料沒有被此分支讀取或更改。
