# P40-16R｜折讓後維持日常財務功能：依來源單號的隔離交易驗證

**候選分支僅有虛構 PostgreSQL 16 測試；不載入正式 ERP、不連正式 Supabase、不更改 main/beta，不使用任何真實建商、請款、薪資或銀行資料，也不部署折讓入帳。**

## 為何要做這一階段

P40-16Q 的安全切換在隔離環境達到 125/125 PASS，但它在折讓事件發生後，會停止所有日常財務資料的全量 JSONB 修改。這對正在大量輸入的正式 ERP **不能接受**。P40-16R 因而以「虛構原單 + 不可變事件 + 來源連結 + 雙版本 CAS」驗證，是否能在折讓發生後依業務類型持續處理收款、保留款、材料應付、薪資和銀行。

## 僅隔離資料庫：以一筆虛構請款測試

`.p40-16r-tests/isolated_accounting_commands.sql` 在 disposable `p40_16r_ci` 的私有 schema `p40r_lab` 建立：
- 唯一虛構單據 `SYNTH-R-BILL`，原金額 632100；示例虛構折讓 32100 後有效金額 600000。**這些不是酷舍任何真實核定金額，也不是合法發票或折讓單。**
- `fake_summary` 只存虛構原始總額、有效總額、發票額與折讓憑證額、收款、保留款、應付與已付、薪資及已付、抽成已核計、銀行進出、`sync_version`、`ledger_version`；透過 SQL CHECK 保證基本不等式（已收款不超過有效額，付款不超過應付，銀行進出等於已記錄付款）。
- `fake_events` 不可直接 UPDATE/DELETE。虛構受控交易 `post_action()` 以 PG row lock 鎖原單，檢查**兩版號**、來源事件引用、操作鍵冪等、授權來源，並在同筆交易追加事件與更新投影。
- 合成 `p40r_operator` role 只能 EXECUTE 模擬入帳函式與 SELECT，不能對原單或事件直接 DML；`p40r_viewer` 只能 SELECT。這是**CI 專用兩個獨立 PostgreSQL 登入**，不等於 Supabase Auth/共用 authenticated/JWT/RLS 的安全設計，絕對不可原樣部署。
- 所有虛構識別、來源與證明必須 `SYNTH-*`，其餘資料被拒絕。

## 分類測試規則

| 類型 | 模擬安全處理 | 正式仍欠缺什麼 |
|---|---|---|
| 每日施工／材料使用 | 即使假折讓已記錄，仍可追加假施工、材料事件 | 沒有正式施工量、庫存、採購成本、業績、重複請款與薪資規則 |
| 未開發票折讓 | 必須有 `SYNTH-APPROVAL-*` 證據；原總額保持不變，模擬有效總額調整 | 不代表任何真實建商簽認或已核定折讓 |
| 已開發票折讓 | 必須以原發票事件與 `SYNTH-CREDIT-*` 憑證同筆留痕，不接受只改原請款金額 | 沒有台灣實際折讓證明、申報月份、發票號碼拆分與稅率計算 |
| 已收款後再折讓 | 禁止自動折讓，標記必須專案人工會計核對 | 退款、溢收、支票、應收沖回、銀行對帳需另外設計 |
| 應收收款及保留款收回 | 每筆需來源發票／保留款設定，不能超收，與銀行流入在同交易更新 | 保留款含稅/未稅、5/10%、不同原單／跨區的完整計算未實作 |
| 材料／廠商應付及付款 | 先有應付來源，付款不可超額，銀行流出與已付同交易 | 庫存、期初、材料廠商合併、付款手續費未實作 |
| 薪資／已付薪資 | 先有薪資來源，付款不可超額；已付款事件不可 UPDATE/DELETE，折讓不會自動改已付薪資 | 真實每月薪資、員工拆分、已付薪資沖回與合法補薪需單獨流程 |
| 抽成 | 只有在**明確審核**的未稅基數與抽成比例對得上金額時才記錄 accrual；如 14000 × 50%=7000，兩位員工各 25%=3500 | 無自動按員工人數除以二，不自動改已付薪資；實際抽成仍需依收款解鎖/原單核准 |

**特別注意：** 上表的操作只保護一張假原單與簡化投影，不包含完整 ERP 真實多案場、多戶別、多原單、多月份發票、稅額或部分收款時的每原單分配。這不是可用於正式財務的「完整折讓入帳功能」，不能直接發布。

## 試算與正式入帳的界線

- `P40-16R PASS` 的意思只是**虛構 PostgreSQL 交易**可以根據來源 ID、金額、冪等和雙版本機制禁止指定錯誤，並讓部分日常操作在假折讓後繼續運作。
- 若未來仍以整份 `erp_states.data jsonb` 作財務權威，新事件與既有 JSONB 之間需要可靠的一致性轉換；先前 P40-16I/O 已確認 legacy direct write 與未受 ledgerVersion 管制的風險，本階段沒有改任何正式寫入途徑。
- 真實 Supabase Auth、MFA AAL2、membership、PostgREST RLS/GRANT，與真實委派會計角色的逐原單權限尚未完成；此 SQL `SECURITY DEFINER` 僅是 CI 假帳號用，**禁止複製到正式 public API**。正式應遵循最新 Supabase RLS、privileges 與 function hardening 文件。
- 本階段不會讀任何真實業務金額或試圖核定耀時代M區含稅折讓；真實對外 A4 PDF、跨區原單、18 項施工明細、發票隱私欄位、薪資抽成及銀行資料均保持原樣。

## 發布前仍需完成

1. 把真正日常業務完整對應到安全受控寫入（案場、多戶別、每日施工、請款/應收、多張發票、合法折讓、材料與庫存、薪資及抽成），逐原單與會計核對。
2. 在**完全獨立的測試 Supabase** 用真實身份／同角色驗證 shared `authenticated` role、JWT/MFA/會員、RLS、資料直寫和所有舊客戶端相容；目前不修改正式 Supabase。
3. 依最初要求先完整安全備份、最新 SYNCED、完整 CI 與正式程式手機/電腦、對外請款 PDF 全流程回歸；**所有檢查 PASS 之後仍需新的具體正式發布與真實帳務寫入授權**。
4. 目前正式 ERP 仍維持 P40-15C 唯讀折讓試算；所有 P40-16A～R 草稿不能整批合併 main/beta。

**下個 P40-16S 如要繼續，只適合在隔離資料與原始會計規則已核對的前提下，把多原單/多發票/部分收款的憑證關聯加到假事件模型；正式版繼續不可入帳。**
