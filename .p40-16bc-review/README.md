## 2. P40-16BC 的隔離實作範圍

`.p40-16bc-tests/mock_policy_authority.cjs` 是從 P40-16BB **未改動複製**的原虛構權限契約；`.p40-16bc-tests/availability_queue.cjs` 以一個**沒有網路或資料庫**的虛構核准人清單測試誰能接受待審任務：

| 虛構情境 | 候選預期處理 | 會變動正式帳務嗎？ |
|---|---|---|
| 會計送審，另一位 owner/admin 可用 | 只能指派同公司、此單文件 ACL、有效假 AAL2、非編輯者／送審者且目前有核准資格者。候選 B 只允許 owner | 否 |
| 只有一人為 owner 且同時編輯與送審 | **安全待審** `SAFE_HOLD_NO_REVIEWER`。不能自行核准，也不能用 MFA、管理角色或備註代替獨立審查 | 否 |
| owner 編輯，但有另一位獨立 admin | 候選 A 可以指派這位 admin；候選 B 不允許 admin，因此仍待審。**兩者如何選擇需負責人正式決定** | 否 |
| 核准人離職、停用、MFA 失效、失去公司或文件權限（在核准前） | 不能沿用原指派；將待審任務重新指派給仍符合權限的其他人，**沒有合格審查人就停止** | 否 |
| 已核准後、實際交付前核准人權限撤銷 | **本次隔離方案採保守暫停交付，標示需制定正式政策**。既有已核准文件在核准人離職後是否仍具法律／內控效力未獲公司決定，不能靠模擬測試替代政策 | 否 |
| 已確認舊請款未修改、尚無新核准人 | **保持原正式列印相容規則**，不追溯把正常已確認文件全部擋住；公司／文件既有權限及原單一致性仍需遵守 | 否 |
| 已確認舊請款另存新版本 | 新版重新核對版本及獨立審查；舊版本應由原歷史查閱路徑唯讀保存 | 否 |
| 假裝 admin、偽造公司、假 JWT、跨公司、員工、無文件 ACL | 全部拒絕核准、指派及資料瀏覽 | 否 |

**這不是新的正式公司角色制度。** 「owner/admin 可核准」與「僅 owner 可核准」都沒有確認；「唯一負責人是否有例外」不能為了方便就在程式中開隱性自核准。

### 為何核准人指派還不是「核准」？

`nominate()` 只分派一個**模擬候選核准者**，不產生任何帳務或簽署效果。 `review()` 必須再次檢查當前假公司、文件 ACL、AAL2、session、角色、版本及來源 SHA-256；若核准者被撤銷或目標改由另一人審核，舊指派即不能核准。新版本不得沿用舊指派或舊核准。

`releaseCheck()` 至多回傳 `NEEDS_SEPARATE_PDF_BYTES_CHECK`；**沒有生成或交付任何 PDF，也不會停止原生瀏覽器 File→Print**。對於核准後離職的情境，本階段僅驗證**保守持有**的一種風險政策，不是說法律一定要求既有核准失效。

全部測試用的 `signatureVerified`、`issuerVerified`、`audienceVerified`、`expiryVerified`、`sessionValid` 等布林值只是**虛構測試設定**，沒有實際 JWT 密碼學驗證、Supabase session、會員資料查詢或 RLS。正式可信來源與權限授權模型仍是缺口。

## 3. 此階段希望負責人稍後決定的 5 件事

1. 核准者採 **A：owner 或 admin**，還是 **B：僅 owner**？不論選哪個候選，預設審查人都不能與最後編輯／送審者同人。
2. 若公司當時只有一位編輯／管理者，是否要指派另一位具身分、MFA、公司及文件權限的正式核准人？在取得正式政策前，**新請款重編維持待審，不能自行簽核**。
3. 核准者**之後**離職或改權限，過往核准要保留效力、重新審查，或僅對尚未交付的最新文件暫停？此議題需要公司業務／法務制度決策。
4. 既有已確認／已開發票／已收款及封存的文件，什麼時候要轉入新核准規則？研究候選只在「另存新版本」時切換；不能動帳。
5. 真正議價折讓改價是否走另外的會計核准，而不是施工明細重編核准？候選建議必須分開，以免未稅、稅額、保留款、發票、銀行、薪資抽成遭誤改。

機器可讀決策 `.p40-16bc-review/decision.json` 保留所有項目 `NOT APPROVED`，不會把模擬 PASS 當成公司批准。

## 4. 純虛構測試對安全風險的界限

`.p40-16bc-tests/test_availability.cjs` 以 Node.js 內建 runner 對角色選擇、唯一 owner、自行核准、owner→admin 指派、owner-only 政策、公司及文件權限、MFA 或 session 撤銷、指定核准人改派、資料來源 SHA／版次變動、舊已確認文件相容、交付前權限重新查核和稽核 metadata 不洩漏私人原單作否定與正向測試。

此測試不含任何真實公司、員工、建商、原始施工品項、薪資、發票號碼、銀行、ERP JSONB 快照或實際登入操作。正式端的一般請款列印、簽章與歷史路徑依舊不變。

**尚未解除的正式發布阻擋：** 沒有真正核定的一份請款的可信資料來源、後端 JWT/MFA/公司+單筆文件 ACL/RLS 實作、正式受信任核准人與持久不可任意改寫的核准紀錄、完整建商備註隱私檢查、PDF-byte 單頁／章印／原細項與交付同檔驗收、最新 SYNCED、可還原備份、手機／電腦及所有發票／保留款／折讓／銀行／薪資抽成回歸、負責人另行明確正式發布授權。
