## 1. 這次真正測試的是正式版原有業務規則

測試直接載入 **未修改的正式** `assets/js/external-billing-invoice.js` 與 `assets/js/billing-group-discount-preview.js`，並從正式 `assets/js/external-billing-print.js` **逐字擷取原有的** `validate(payload)`、`originalTemplateView(payload,d)` 兩個函式執行，不另造會與正式版產生差異的計算器。

建商版的一筆跨區文件至少由兩張原單及其應收／收款快照組成。正式 `validate` 必須證明：

- 各原單：未稅 `untaxed` + 稅額 `tax` = 含稅 `grossTotal`；含稅減保留款 = 本期應收；已收加未收 = 應收；保留款已收加未收 = 原保留款；待收可收加支票預留 = 未收。
- 合併數字：11 個總計欄位均與各原單／收款快照之和完全相等，不得「重新用當前稅率」或「套用目標區的保留款比例」算回去。
- 每筆施工：`Math.round(qty*price) === amount`、四位小數邊界、資料筆數、來源原單、原單公司／客戶一致；統一明細的未稅/含稅目標與來源合計相同。重編明細必須有核對理由，但**文字理由本身不等於正式人員已核准**。
- 對外 View：僅顯示 `displayProjectName` 指定區域，保留施工戶別和項目名稱、備註與原核定金額；個別原單發票號碼、開票月份、其他區域與來源快照不得出現在**一般對外建商版**。
- 發票：正式 `KusheExternalBillingInvoice.project()` 在**內部**維持原單的 8 月、10 月發票對照，不新增發票、應收或修改原單。不同月份發票不得「合成」一張對外發票。
- 折讓：正式 `KusheBillingGroupDiscountPreview.preview()` 標示 `readOnly: true`／`canPost: false`，只是建商核定額減原含稅請款的**試算差額**；目前稅額分配、保留款分配及應收調整仍是「待核對」。測試必須確認它**不能改寫請款、收款、銀行或對外 PDF 金額**。

## 2. 真正測試資料與負面情境

全部使用 `.p40-16av-tests/fixture.cjs` 的 **FAKE** 來源：兩個來源區域 L／M、指定只顯示 M 區、8 月與 10 月的**虛構**原發票號碼哨兵、施工戶別、計價項目與保留款。

`.p40-16av-tests/test_original_financial_integrity.cjs` 由 Node test runner 檢查：

- 正面案例：未稅、含稅、免開發票、四位以內小數數量、兩月各自開票、18 筆施工明細等，確認原數值、完整原戶別、單位、數量、單價、每列金額都不變。
- 金額破壞：原稅額、含稅總額、保留款、應收、已收與未收、待兌現支票及可收款不一致，以及統一明細數量、單價、單列金額或總目標變更，都應被正式驗證器拒絕。
- 來源破壞：重複原單、收款關聯錯誤、不同客戶、指定案場找不到、原單重複、同客戶原單不足、文件封存、原施工明細刪除等，不能裝作可正常輸出。
- 內部發票對照：8 月與 10 月兩份虛構發票號碼、月分與原核定金額仍保存在內部 `invoice.project()`，但不應進入建商版 View。
- 議價折讓：核定額超過原總額、原請款／應收／收款快照遭變更，應阻擋試算；已開發票、已有收款、支票預留須提示重新查核，不能自動入帳。
- **安全缺口明確記錄：** 正式 `originalTemplateView()` 直接使用 `d.note` 當對外備註，**沒有保證能去除使用者手動輸入的原發票號碼或其他區名稱**。本階段另外示範了一個**只存在測試中的**隱私欄位/文字哨兵拒絕規則。這項規則**尚未加入正式 ERP**；如果備註真的包含私密資訊，仍需正式候選及人工驗收。

## 3. 本階段不會解決的正式風險

這項測試只證明**官方函式在經核定且一致的合成來源上有財務與隱私投影檢查**，不代表正式 Supabase 已有單筆可信讀取服務。P40-16AT 及 AU 已確認：正式系統仍以 ERP 狀態快照為主要來源，單筆請款可信寫入/同步、真正 JWT／MFA 伺服器端驗證與公司文件權限需要另行設計與核准；AU 的 PostgreSQL RLS 40 項 PASS **僅為虛構資料庫模型**。

本階段**沒有**產生正式 PDF、更新議價／折讓或財務數字、發票入帳、修改應收、保留款、銀行、薪資或抽成，也沒有操作正式資料庫。程式碼依原有來源校驗，對外 View 不是可信已核准的可寫入原帳明細。

若未來要求將議價/折讓差額真的修改已送出請款，不能由 PDF 轉換步驟自行重新分配稅、保留款或員工抽成，必須另行獨立設計會計核准、金額分攤及可回復的帳務流程，並取得使用者明確授權。

## 4. 下一道正式發布的門禁

- 可信、唯一且**具版本控管**的單筆核定資料來源（不可把整份 ERP 備份直接送新 PDF 網關）。
- 真正伺服器端 JWT／MFA、公司與文件層級 ACL，不可相信客戶端傳入的核定 View。
- 對外備註、重編明細理由與來源發票等欄位全面白名單／人工核對；不僅過濾 `PRIVATE-` 這種測試字串。
- 所有方案的實際 PDF bytes 單頁、全部原施工項目、原核定稅額保留款及章位／真實手機和電腦驗收。
- 當前 `SYNCED`、完整可還原備份、`main` 最新差異與所有 CI PASS，以及負責人**另行明確同意正式發布**；任何一項不符都必須停止。

**P40-16AV 結論：只允許在 GitHub CI 對虛構原單實際執行正式函式，不修改任何正式業務資料；即使測試全部 PASS，正式 PDF 可信來源與所有上線門禁仍 BLOCKED。**
