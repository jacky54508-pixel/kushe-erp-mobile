基準：2026-11-18 當時正式 `main` `2ab9c9d5944b1360ba3eebf49695713168caca8a`、`beta` `62669539053a15174081ba8670b18248195c6f8c`。本分支沿用 P40-16AH～AL 的獨立測試程式，新增 P40-16AM 檔案及 CI，不修改正式網站、正式 PDF HTML、IndexedDB、Supabase、雲端同步、薪資、銀行、發票、應收或任何實際資料。

## 1. 正式程式的現有規則（唯讀擷取驗證）

- `assets/js/external-billing-print.js` 的正式 `validate(payload)` 會驗證 `kushe-external-billing-group-v2` 的來源原單、結算快照、同客戶、指定 `targetBillingId` 與 `displayProjectName`、施工小計及合併總額一致。
- 其正式 `originalTemplateView(payload,d)` 將已驗證的一般對外跨區文件轉為 `kushe-external-document-v1`：`project` 與 `mergedBillingProjects` **僅有指定 `displayProjectName`**，不包含源自不同月份原單的 `invoiceNo`、`invoiceDate`、`sourceSnapshots` 或原發票對照表；單據原始金額／保留款／應收不另重算。
- 正式 `assets/js/external-billing-invoice.js` 的 `project()` 只用於原單對照計算，P40-16AM 真正呼叫這段未改動的正式程式，但其原票號資料**不傳入 PDF renderer**。
- 舊的封存／歷史保存版本仍有獨立的原發票對照表展示路徑。**P40-16AM 明確拒絕這類文件**，不將其當作通常可交付建商的對外 PDF。
- 正式 `billing-print.html` 的密集施工明細／最下方施工項目彙總是既有列印規則；本研究採用獨立版面驗證功能可能性，**尚未完成與正式 PDF 逐像素逐字視覺等效**。

## 2. 測試如何隔離

1. GitHub Actions 在本機由**正式原檔**擷取 `validate()`、`originalTemplateView()` 函式本體到測試執行時的 `runtime_official_extract.js`；使用後刪除該臨時檔。沒有修改、替換或提交原正式函式。
2. 在 localhost 的 Chrome 測試頁載入原本 `external-billing-invoice.js` 及以上正式函式，使用**完全虛構**兩／三張原單（來源區域 L、K、指定區 M；來源日期模擬 8、10 月）、各自結算來源及內部發票號碼哨兵。
3. `cross_zone_contract.js` 要求來源驗證通過、非封存、單一指定區、來源施工明細每筆和正式輸出**逐筆一致**、所有核定總額／保留款／應收與已驗證來源相等。僅建立一個全新白名單對外物件，**不攜帶其他來源區名與內部發票快照**。
4. `cross_zone_pdf.js` 使用 `pdf-lib@1.17.1`／`fontkit@1.1.1` 由瀏覽器**本機真正產生 PDF bytes**，只打印指定區、施工來源戶別／項目與最下方彙總。無法放進 A4 的長品名／長備註／明細一律擋下，不隱藏欄位、不用低於 8pt 的字體。
5. PyMuPDF 開啟實際產生的 PDF，驗證 A4 頁數與尺寸、所有虛構戶別及項目、核定金額、僅指定區、沒有其他區名與內部發票哨兵、文字不越界、最低 8.1pt、模擬 LOGO **18×14 mm** 與模擬大小章 **54×24 mm**。**沒有真實公司 LOGO 或印章**。
6. 正式公司帳務／雲端一律不查詢；繁體字型只在 CI 安裝並立即刪除，不提交或提供字型檔。上傳短期 GitHub Artifact 只有通過的**虛構** PDF、預覽圖與結果 manifest。
