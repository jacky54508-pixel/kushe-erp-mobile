# P40-16D｜追加式折讓台帳、CAS 與回沖（純模擬、不可入帳）

**本階段僅虛構資料與純函式演練。** P40-16D 沒有與正式 ERP、Supabase、薪資、發票、應收、銀行或任何雲端資料相連，沒有可對正式帳務生效的按鈕或 API。正式 `main`、`beta`、`index.html` 不動。

## 1. 設計目的

P40-15C 已能試算 632,100 → 600,000，折讓 32,100。P40-16A/B/C 增加人工原單分攤、發票及會計憑據檢查與回沖前置核對；但它們沒有入帳交易、冪等或帳務紀錄實作。本階段只用**虛構測試資料**驗證未來追加事件的邏輯能否阻擋重複折讓、版本落後、跨文件回沖、歷史事件遭竄改等錯誤。

## 2. 模擬台帳結構

```text
SimulationLedger { schema, revision, events: [
  { revision: 1, kind: SIMULATED_ALLOWANCE,
    eventId, operationKey, documentId, basisSnapshot,
    fingerprint, deltas, sourceDeltas[], reversesEventId: null },
  { revision: 2, kind: SIMULATED_REVERSAL,
    eventId, operationKey, documentId, basisSnapshot,
    fingerprint, deltas, sourceDeltas: null, reversesEventId }
]}
```

- **追加，不覆寫**：`simulateAllowance` 只在傳入模擬台帳的複本上追加一筆虛構事件；原陣列不可更改。每張原單的折讓（未稅、稅、含稅、保留款、應收）合計必須等於核定差額。
- **唯一識別與冪等**：`operationKey`、`eventId` 在全台帳必須唯一。同操作鍵與相同事件內容重送，在模擬中回傳既有結果、不新增事件；同鍵不同內容則拒絕。
- **樂觀版本檢查**：要求 `expectedRevision` 等於現有模擬台帳版本，另外要求原單快照一致，否則停止。這只是**CAS 原理示範**；實際多人同時寫入，必須由未來真正的資料庫交易／原子比較交換／唯一索引保證，純函式無法提供並行安全。
- **回沖**：`simulateReversal` 只追加單獨的 `SIMULATED_REVERSAL` 反向事件，唯一引用原事件並檢查回沖不可重複。原發票、原收款、銀行與抽成完全不改。
- **模擬餘額**：`projection` 從模擬事件計算淨折讓；追加模擬回沖後，淨折讓恢復零，但事件仍保留兩筆。

## 3. 稅務、帳務、員工抽成仍為人工門檻

1. 本案例含一張已開發票原單，折讓憑證與營業稅的合法處理方式仍須會計依原票、申報狀態、買受人類型、紙本或電子發票核對。
2. 折讓 32,100 在合併請款上僅是整張總額；正式要入帳，必須確認**每張原單**減少多少未稅、稅額、保留款與應收。測試裡的兩張分攤僅為虛構，並不是實際核准的分攤。
3. 已收款、支票預留與已收保留款的處理，必須制定獨立沖帳／退款程序，不能覆寫銀行交易。
4. 員工抽成目前以未稅來源及原有收款解鎖規則為準。折讓前、後如何影響未付款／已付款的抽成，尚未取得核定，不得自動重算。

## 4. 正式寫入前必須另外完成的實作

- 建立**獨立**的真實折讓台帳及原始請款／應收／發票關聯約束。
- 資料庫層級的唯一操作鍵、原子 CAS、同鍵不同內容拒絕、重送同內容不新增事件。
- 針對真實發票折讓證明、會計授權、稅額與申報處理，以及必要的沖回／退款建立可稽核流程。
- 明確採用**調整事件**的應收與保留款投影，不能直接把原請款金額覆蓋。
- 完整回歸：報價 → 請款 → 應收 → 收款 → 銀行，材料、薪資、抽成、發票、保留款、PDF 與跨裝置同步。
- 正式 SYNCED、完整可還原備份、main 差異及 CI 全 PASS，**重新取得明確的正式寫入／發布授權**。

## 5. P40-16D 安全限制

- `assets/js/p40-16d-ledger-simulator.js` **不載入**正式 `index.html`，沒有瀏覽器儲存、Supabase、網路或 Store API。
- `canPost=false`、`canSave=false`、`mutationCount=0` 永遠維持。
- `SIMULATED_ALLOWANCE` 和 `SIMULATED_REVERSAL` **不是**正式入帳或真實折讓憑證。
- 模擬指紋採規則化 JSON 比對，**不是密碼學簽章**；實際部署另需後端交易式檢查與權限／稽核機制。
- 不修正或上傳任何正式資料；任何安全測試失敗立即停止，禁止 main/beta 合併。

**建議後續 P40-16E**：在隔離資料庫（非正式 Supabase）驗證真實交易下的唯一鍵、CAS、重送及回沖競態，再規劃經會計核定的原單分攤帳務投影；尚不能進入正式入帳。
