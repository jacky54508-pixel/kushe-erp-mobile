## 二、已完成的隔離實驗

`.p40-16ay-tests/persistent_approval_lab.cjs` 是一個**Node.js 本機、完全虛構資料**的持久化核准模型。它執行正式 `assets/js/external-billing-print.js` **逐字原本的 `validate()`** 查核原施工明細、稅額、保留款、已收、應收、來源一致性；另以 SHA-256 核對**整份測試文件**的簽核指紋。

- **保存核准證據：** 使用在 CI 作業系統暫存目錄的 JSONL 追加式檔案，記錄 `ENROLLED`、`REVISED`、`APPROVED`，由順序編號及前一筆 SHA-256 構成 hash-chain；寫入時採 `fsync`，避免只留於 JS 記憶體。重新啟動讀取時會重算每筆指紋和事件轉移；檔案損毀或缺字節會拒絕，不自行修復或略過。並用本地排他鎖阻擋同時寫入；舊視窗用過期紀錄提交時會拒絕。
- **不儲存私人文件在稽核：** 日誌只記錄假公司、假使用者、文件 ID、版本、內容指紋與操作，不包含原施工列、8 月/10 月發票號碼、收款、備註或整份 ERP snapshot。正式版若要保存完整帳務審核證據，須另外核准保存範圍及存取權限。
- **舊文件安全銜接：** 設計上標示為 `legacy` 的**既有、未改動**有效版本，可維持原列印判斷，不會因為沒有新式雙人簽核而全面停用；重新保存新版本後，該新版本自動進入 `enforced`。舊版本仍由**原正式列印的歷史路徑**處理；本模型不去改原正式列印程式。
- **新版本核准：** 若原施工明細與對外統一明細有不同，需由同公司、已取得這份文件授權、測試 AAL2 的另一位 owner/admin 核准；新增版次、改品名、戶別、單位、數量、單價、順序、備註、指定區、原發票號碼、付款/保留款快照、總額或核對理由，**舊核准一律不授權新版本**。假規則中編輯者不能自行核准。
- **重新開啟安全：** 重啟後日誌依 hash-chain 復原核准狀態；但**不會把原單、收款、PDF 或私密資料寫入日誌**，必須由假可信來源再次提供與指紋相同的文件，才允許評估新列印權限。
- **既有正式保護：** 檔案在 `.p40-16ay-tests/`，僅在 GitHub CI 預設暫存目錄寫入；不在正式 `assets/js/`、`pages`、`supabase/migrations`、或任何使用者的 ERP 資料中建立核准表。

### 重要限制：此機制不是可上線的不可竄改稽核系統

SHA-256 hash-chain 能發現單筆任意修改或不完整寫入，**不能防止擁有檔案寫入權限的人整份重新產生合法鏈**；缺少受信任時間、外部不可竄改錨點、簽章、真正 JWT/MFA、公司成員 RLS、審查人權限、交易式資料儲存、審核人身份獨立性證明，以及正式 Supabase 的真實單筆請款來源。本機檔案鎖只演示同機排他寫入，並非分散式交易或正式多人併發能力。

**這次 owner/admin 可核准、accounting 可編輯、必須與最後編輯者不同的規則只是實驗中的預設，並不是已獲使用者核定的公司內控制度。** 真正部署前需決定：是否必須雙人覆核、歷史已確認文件如何補核、誰能處理離職人員或權限撤銷、哪些修改要撤銷先前的批准，以及是否保留原有歷史列印無核准入口（可能的風險需特別註明）。

1. **可信單筆資料來源／核准來源：** 正式 Supabase 現況是 ERP JSONB 快照為主要資料來源，P40-16AT 中繼資料查核未發現已核准的單筆請款 PDF API；此模型不能從真實 ERP snapshot 自動產生可信摘要。
2. **真正可稽核保存機制：** 本次 JSONL 只屬 CI 測試；正式須獨立核准伺服器端 JWT/MFA/公司/文件權限、避免自行設定 claims、RLS、持久核准日誌及審查行為的不可否認證據。任何正式 SQL/DB schema/RLS 變更須另經明確授權。
3. **舊文件的實際數量與特例：** 尚未從正式資料統計既有不同版次、v1/v2 格式、重編原因、封存／已開發票／已收款情況；不可未驗收就全面啟用新門禁。
4. **對外內容安全：** P40-16AW 的原發票／跨區隱私備註阻擋仍只在草稿候選，未合併；真正 PDF bytes 單頁／章印／完整施工明細與品牌也尚未驗收。
5. **正式發佈程序：** 必須當下最新 `SYNCED`、完整可還原備份、正式 GitHub main 和所有 CI、真實手機與電腦驗收、完整請款／應收／折讓／保留款／發票／銀行／薪資抽成回歸，以及負責人**再次明確批准正式發布**；任一未通過即 STOP。
